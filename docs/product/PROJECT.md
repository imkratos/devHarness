# DevHarness CLI 维护范围草案

**来源与边界。** 用户在项目评审后提出「仔细分析一下，然后修复吧」。原始请求见 `.harness/runs/toolkit-maintenance/state.json` 的 `request`，评审基线为 `7a4eca7`。本次维护现有工具包，使用者是安装或升级工具包的项目维护者，以及通过 CLI 推进和恢复任务的主控。交付范围仅含命令行行为与演练，无图形界面。

**M0 与修复的衔接。** 主控将本草案与 M0 规划一并提交用户确认。M0 在隔离样例中验证现有安装、启动、检查与恢复入口，记录基线提交、实际命令、退出码和日志。M0 验收后，后续修复沿用原始请求，按下列 AC 取证。前五项对应本 run 的 `evidence/reproduce.log`，第六项是补充演练。本草案尚未执行这些验收。

| 编号 | 评审场景 | 后续修复的验收条件 |
| --- | --- | --- |
| AC-01 | 安装器在手工合并后仍将同一文件列为冲突，缺失文件无法补齐。 | 未处理的冲突须列出路径并在复制前停止。维护者明确确认已合并的文件后，重跑保留合并内容并补齐清单中的缺失文件；再次运行无新增变更。 |
| AC-02 | `bugfix` 使用空验收清单仍从 `reproduce` 进入 `implementation`。 | 清单为空或缺少任务引用的 AC 时停在复现阶段；补齐后才可推进，并冻结 AC 编号、需求引用、场景、预期和验证方法。后续可补状态与证据；删项或改动预期须回到复现阶段。 |
| AC-03 | 任务输入路径相同、文件内容已变，旧任务包仍可继续。 | 冻结任务依赖的规范、复现记录等依据；同路径内容变化时，恢复到最早受影响阶段并使下游证据失效。授权修改的实现源码即使在任务输入中供阅读，也允许正常编辑；该编辑不触发重新规划，测试须覆盖修改后的版本。 |
| AC-04 | 仍有待办任务时，`implementation` 可被标记完成。 | 给定两项实施任务，仅一项 `done` 时，推进应停在实施阶段并指出未完成任务；两项均为 `done` 且其余门禁满足时才能推进。 |
| AC-05 | 同一 Feature ID 和 change ID 下，不同原始请求会被当作重复请求。 | 相同请求及关联标识重试时返回原 run；沿用这对标识但更换请求时，CLI 应报告冲突，保留原请求和进度，不创建重复 run。 |
| AC-06 | 真实源码变更后的回退与恢复演练。 | 在隔离样例保留一次通过记录，实际修改并提交已测源码，使一项既有行为失败。运行 `resume` 核对最早受影响阶段、下游证据及批准失效，再运行原验证命令观察失败。修正源码后重新推进并取证，遇人工门禁须重新确认；用提交差异、阶段记录和前后日志串起全过程。 |
