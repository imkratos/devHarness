# 工作流 v2 节点约定

主控读取 `.harness/PROTOCOL.md` 和所选 workflow JSON。在项目根目录使用 `python3 .harness/scripts/harness.py`，命令及参数见 `.harness/cli.md`。人工确认记录用户原话、时间及本次确认的全部产物路径、版本和 SHA256。只有主控登记状态、批准、路线图。

## 从原始需求到 M0

- `product-analysis` 保存原始需求的可追溯引用，写产品草案，标出假设和待决问题。`domain-modeling` 从草案提炼领域边界。`roadmap-planning` 将原始目标映射到里程碑、Feature ID 和 M0 验收条件，主控向用户一并展示产品草案和 M0 规划，取得覆盖两者的明确批准后建立基线。批准绑定保存在 run 中的规划快照。后续交付进度由主控更新路线图。若初始化源于开发请求，M0 获批后按原始需求继续，关联初始化 run、里程碑、Feature ID 和 change ID。
- `design-system` 对有 UI 的项目提交可运行原型并由用户确认。仅当已确认范围明确无 UI 时，主控绑定范围产物及哈希并记录理由，按 CLI 登记无 UI 的明确批准后记为 `skipped`。范围不明确时先澄清。
- `architecture-design` 由主控核对方案与已确认范围、UI 约束和技术证据；涉及产品或 UI 决策变化时回到相应门禁。`bootstrap` 验证可运行骨架和 M0 路径，`project-review` 展示整合版本、验收结果与证据，等待用户最终批准 M0 后更新路线图。

## 功能、修复与重构

- feature 的 `product-analysis` 用原始需求、路线图和已有规范建立 OpenSpec 变更，将需求引用关联至 AC，由用户确认。`ui-design` 有可见变化时确认交互和截图基线；无 UI 时绑定已确认的范围与理由，按 CLI 登记有效批准后记为 `skipped`。复用相同 UI 时核对当前场景、状态与交互全部已覆盖，引用来源 run、阶段、有效批准和完全相同的产物集合、版本、哈希，复用 UI 记为 `passed`，复用无 UI 决定须适用性一致并记录理由；有差异或批准缺失时重新确认。
- bugfix 的 `reproduce` 只复现定位，输出复现步骤、期望行为依据和失败证据。refactor 的 `impact-analysis` 输出影响范围、应保持的行为和风险。主控在各自首阶段完成前据此写入本 run 的最小 `tasks.json`，包含任务 ID、执行角色、依赖、输入、写范围、行为依据、AC 和验证命令。bugfix 同时准备供最终验收的 `acceptance.json`。若目标改变业务行为，转入 feature 需求确认。
- `test-plan` 从原始需求和行为依据独立设计测试，允许在实现前记录预期失败。`implementation` 在 feature 中按 `tasks.json` 派发，修复和重构使用首阶段形成的任务包。默认串行，写范围无重叠且依赖就绪时，在独立 worktree 确认 cwd 后最多 3 并发。主控整合后在整合提交执行 `test-feature`，`review-change` 核对真实差异和证据，`accept-feature` 按当前工作流在实际产品逐项验收并请求用户批准。
- `archive` 是 feature 的主控步骤。先核实已验收的 change ID、活动变更、归档位置和正式规范。活动变更已消失、归档唯一且正式规范与批准内容一致时复用证据。仅对待完成的同步或归档执行已安装的 OpenSpec 操作。记录实际命令结果、归档路径与规范差异，再推进阶段。中断后先复查，状态冲突或缺少证据时暂停核实，禁止重复归档或递归执行 `dh-develop`。
- 里程碑内每个 feature 单独验收、归档。创建最后一个功能 run 时标明所属里程碑及最后功能，按其工作流快照在 reflection 后执行 `milestone-review`。主控核对路线图中每个功能、成员 run 和已验收提交均已整合，在最终提交重跑跨功能 E2E、回归及里程碑验收。展示证据并取得用户对该整合版本的最终批准，再将里程碑标完成。失败回到责任阶段，修复并重新整合验证。

## 失效与恢复

核对 run 绑定的工作流版本、提交、输入和产物哈希。上游需求、UI、任务输入或实现变化时保留历史证据，将最早受影响阶段及依赖它的下游回退到待执行状态，撤销相关批准的效力，包括依赖旧依据的跳过和复用。主控重新取证，遇人工门禁等待新的明确确认。环境或权限缺失记 `blocked`；执行故障重试当前阶段，代码缺陷返回实现，需求或 UI 变化返回对应确认阶段。缺少对应阶段时按该路线重评或转 feature。记录原因、下一步和尝试次数；达到重试上限后阻塞，查明原因后再按 CLI 显式重开。

对旧 run 或缺少版本的 run，先只读展示旧状态、产物、批准和兼容性缺口。需要接管时按 `.harness/cli.md` 显式迁移，保留原记录和证据，从 v2 起点逐阶段复核；未经复核的通过或批准不得沿用。
